# Ticket label descriptions

All ticket text in this project is **synthetic English**, generated by `scripts/generate_tickets.py`. It is not real employee or student data.

## Classes

Exactly six labels are used, always spelled this way:

| Label | Typical issue |
|---|---|
| `Account` | Login, password reset, locked/disabled account, two-factor authentication, profile access |
| `Network` | Wifi, VPN, slow or dropped internet connection, shared drives, ethernet |
| `Hardware` | Laptop, monitor, printer, keyboard, mouse, webcam, docking station, battery |
| `Software` | Application crashes, licenses, installers, updates, sync errors |
| `Security` | Phishing, suspicious login, malware, credential sharing, permission changes |
| `Other` | Anything that is not a technical issue: office requests, policy questions, feedback |

## Why this is not a trivial classification problem

The classes deliberately **share vocabulary**:

- `password` and `login` appear in both `Account` and `Security` tickets.
- `update` appears in both `Software` and `Hardware` tickets.
- `account` appears in both `Account` and `Security` tickets.
- `connection` / `server` appear in both `Network` and `Software` tickets.

About 8% of tickets in every split use a **paraphrased** template that avoids the most obvious class keywords. A subset of tickets also include a short, class-neutral filler sentence (e.g. "I will be out of office tomorrow afternoon."), which is irrelevant to the label and should not be a useful predictive signal. Because of this overlap, a correct baseline should score well above chance but **not** a trivial 100% F1 — if your model scores 100% on `test.csv`, check for a data leak or an overly narrow vocabulary before trusting the result.

## Splits

| File | Role |
|---|---|
| `train.csv` | 70% of the generated corpus |
| `validation.csv` | 15% — use for model selection / hyperparameters |
| `test.csv` | 15% — report your final metrics on this split only |
| `hard_cases.csv` | A small (24-row) robustness set, not part of train/validation/test |

Regenerate the main corpus with `python3.11 scripts/generate_tickets.py --seed 42` (see `README.md`). Re-running with the same seed must reproduce `data/SHA256SUMS` exactly.

## `hard_cases.csv`

24 rows (4 per class) built for the required robustness experiment. Each row exercises one of these categories (the category is **not** a CSV column — it is documented here so you can discuss it in your report):

`HARD-000001`–`HARD-000018` are grouped in fixed threes, one group per class in class order (`Account`, `Network`, `Hardware`, `Software`, `Security`, `Other`):

1. **typo** (1st id in each group of 3, e.g. `HARD-000001`) — a couple of words are corrupted with a swapped or dropped letter (e.g. "acconut", "passowrd"). This is a spelling-robustness case, not a missing-diacritics case (the course language is English).
2. **paraphrase** (2nd id in each group, e.g. `HARD-000002`) — correct label, but phrased without the class's most common keywords.
3. **irrelevant text** (3rd id in each group, e.g. `HARD-000003`) — the real issue sentence is padded with class-neutral filler before and after it.

`HARD-000019`–`HARD-000024` are **ambiguous keyword** cases, one per class: the text mixes vocabulary from two classes on purpose (e.g. an `Account` login problem mentioned alongside a `Network` VPN problem). The label given is the intended primary class, but a bag-of-words model may reasonably disagree — this is exactly the case you should discuss in your error analysis.
